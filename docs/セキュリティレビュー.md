## 2. 残存リスク(受容した上で公開する)

### R1. 高解像度データはクライアント側で生成されるため、技術的には課金を迂回できる
印影の描画はブラウザの Canvas で行うため、開発者ツールを使える利用者は
自分で 2000px を指定して書き出せる。サーバー側でのレンダリングに移せば防げるが、
日本語フォントをサーバーに持つ必要があり、初期費用0円の制約と釣り合わない。

**受容する理由**: 有料プランの価値は解像度だけではなく、**商用利用の許諾と発行番号つきの
利用許諾書**にある。これはサーバー側でしか発行できず、迂回した利用者は取得できない。
業務で使う法人にとっては許諾の有無こそが本質的な購入理由になる。

### R2. `session_id` を知っている者は誰でも設計値を取得できる
`/api/unlock` は `session_id` を事実上のベアラトークンとして扱う。URL が第三者に漏れると
その印影の設計値(会社名・書体・色)を取得できる。ただし取得できるのは購入者自身が
入力した公開情報の範囲で、決済手段や個人情報は含まれない。B1 seido-web と同じ設計。

### R3. `/api/checkout` にレート制限がない
連続呼び出しで Stripe 側に未使用のセッションが大量に作られうる。課金は発生せず、
Stripe 自身のレート制限と Vercel の標準的な保護が一次防御になる。
**公開後にアクセス状況を見て必要なら対応する**(現時点で費用0円の対策手段が乏しいため)。

## 第6回レビュー(2026-08-09) — 決済の設定要件を1つに減らした変更分

第5回レビュー以降のコード変更のうち、**`api/checkout/route.ts` の設定判定**のみを対象とする。
第1回の結論(R1〜R3の受容)は変更しない。

### 対象
- `src/app/api/checkout/route.ts` — 戻り先URLの出どころを、環境変数 `SITE_URL` から
  `@/lib/site` の定数 `SITE_URL` に変更し、**必須の環境変数を `STRIPE_SECRET_KEY` の1つだけにした**

### なぜ直したか(発見の経緯)

**「鍵を入れても決済が動かない」状態が仕込まれていた。**
`/api/checkout` は `if (!key || !site)` で判定しており、**環境変数 `SITE_URL` が未設定なら、
Stripeの秘密鍵が正しく入っていても `payment not configured` を返す**。
一方この値は `src/lib/site.ts` に**定数としてビルド時に確定済み**で、canonical・sitemap・
構造化データなど**9か所がその定数を参照している**。決済だけが同名の環境変数を別途要求していた。

- **危険なのは、失敗したときの見え方が「未設定」と完全に同一**なこと。
  オーナー様が鍵だけを設定された場合、本番の表示も `/api/checkout` の応答も**今日とまったく同じ**になり、
  「鍵の設定に失敗した」「Stripe側の問題だ」と誤って切り分けることになる

### 実測(対照つき)

**同一のローカルサーバー・同一のリクエスト・`STRIPE_SECRET_KEY` を設定した状態**で比較した。
鍵は **Stripeに実在しないダミー値**を用いており、**オーナー様のStripeアカウントには一切接続していない**。

| 条件 | 応答 |
|---|---|
| **対照: 修正前のコード**(鍵あり・`SITE_URL` なし) | **HTTP 500 `payment not configured`** ← 本番が今日返しているものと同一 |
| **修正後のコード**(鍵あり・`SITE_URL` なし) | **HTTP 502 `payment session failed`** |
| 修正後の502の中身(サーバーログ) | Stripe が `Invalid API Key provided` を返した = **リクエストはStripeまで到達している** |
| 本番(鍵なし・本日実測) | **HTTP 500 `payment not configured`**(12日連続) |

→ **決済の可否が `STRIPE_SECRET_KEY` だけで決まる状態になったことを、実測で確認した。**
ダミー鍵の `.env.local` は検証後に削除済み(`.gitignore` の `.env*` 対象で、そもそもコミットされない)。
